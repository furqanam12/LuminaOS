LuminaOS Documentation

Edition: LuminaOS 1.1 — Aurora Update 1 Documentation revision: 1.0 Last reviewed: 20 November 2026 Audience: new users, VirtualBox testers, developers and release maintainers

Welcome to the official documentation set for LuminaOS. These guides describe the features implemented in the source tree, safe installation practices, compatibility boundaries and the release-verification process.

Read this first: a source test is not the same as acceptance testing a booted ISO. For release readiness, always consult release/RELEASE_STATUS.md, the checksum and the guest-validation results. Compatibility depends on the application, hardware and runtime; no operating system can guarantee every Windows, Android or macOS application.

The generated, professionally formatted versions are:

  • docs/LuminaOS-Documentation.pdf — offline/shareable manual

Regenerate them after editing any Markdown file in this directory:

cd LuminaOS-performance
python3 tools/build-docs.py

If Google Chrome or Microsoft Edge is installed, the script also generates the PDF automatically. Otherwise the always-current Markdown and HTML documentation remain available. No third-party Python packages are needed.

What LuminaOS provides

  • A custom Lumina Shell with desktop, dock, top bar, Start/overlay surfaces, workspaces and notifications.
  • Built-in Files, Settings, Store, Task Manager, Notepad, Calculator, Photos, Snipping Tool, About, Setup and Compatibility Wizard applications.
  • A local, loopback-only desktop API using JSON and Server-Sent Events.
  • Performance controls, accessibility options, window management and persistent per-user settings.
  • Printer and Bluetooth management, CUPS integration, Orca/AT-SPI support and clipboard history.
  • Route-specific runtimes for Windows programs, Android APKs and common Linux package formats.
  • An automated host-test CI workflow and a manually dispatched GitHub Actions ISO build with checksum artifacts.

Documentation conventions

  • Recommended: a tested or safer option, not a mandatory requirement.
  • Warning: an operation that may need administrator access, modify the host or lose unsaved work.
  • Note: an important version, hardware or compatibility constraint.
  • Commands beginning with sudo or pkexec modify the system; understand the action before approving a prompt.
  • Absolute operating-system paths describe the guest, not the Windows host.

Support and evidence

When asking for help, include:

  1. LuminaOS version, host OS and VirtualBox version.
  2. Live session or installed system.
  3. Exact application/package name and format.
  4. The complete error message, screenshots and logs where available.
  5. Output from the relevant checklist in docs/BUILD_AND_DEPLOY.md.

Do not share your API token, password, private SSH key or other credentials in bug reports.

LuminaOS can be run live from an ISO or installed on a virtual disk. For normal daily use, install it to a VirtualBox disk and install Guest Additions.

3. Built-in applications

File Explorer

Use Files to browse your home folder, mounted devices and shared locations. It supports:

  • Grid/list views, search, sort, tabs and split view
  • Create, rename, copy, move and delete operations
  • Undo/redo for common operations and conflict handling
  • ZIP/TAR extraction, ZIP creation, file permissions and Trash restore
  • Recent files, Quick Access and a detailed status bar
  • Open in Terminal and Open in Kali Terminal in the current directory

For package files, use the format-specific procedure in the Compatibility guide.

Lumina Store

Install or remove catalogued applications, inspect package downloads, install supported local package files and apply updates. The Library shows running jobs and their result.

A Windows .exe launch is labelled Launched, not Installed. An Android APK installation is only marked complete after the runtime returns success.

Settings

Major sections include:

  • System and display: host information, theme, brightness preferences, night light and output resolution
  • Sound: volume, mute and system sounds
  • Notifications: focus mode, quiet hours and per-application rules
  • Bluetooth & devices: adapter power, scanning, pairing, connection and removal; pointer speed
  • Network: adapters, Wi-Fi connections and advanced settings
  • Personalisation: theme, accent, wallpaper, dock and effects
  • Power & performance: lock, sleep, restart, shutdown and performance presets
  • Printers: add CUPS printers and choose a default printer
  • Accessibility: interface scale, contrast, focus outlines, animation and screen reader
  • Clipboard: history management
  • Time & language: time zone and 24-hour clock
  • Backup & restore: export/import settings and update preferences

Task Manager and utilities

  • Task Manager: processes, resource use and performance history
  • Notepad: tabs, find/replace, editing and file status
  • Calculator: standard operations and history
  • Photos: image browsing and viewing
  • Snipping Tool: screenshots with capture options
  • About: version and device details
  • Compatibility Wizard: environment checks and runtime setup

4. Accounts and passwords

To create an account, go to Settings → User accounts and enter a unique username, password and confirmation.

  • Use lowercase usernames beginning with a letter or underscore.
  • Passwords must be at least four characters; use a strong, unique password in practice.
  • Account creation assigns a login shell and home directory.
  • Do not delete your active account. Keep a working administrator account.

Changing your password requires your current password. Never send credentials or API tokens in screenshots or support messages.

5. Accessibility

The following settings are available:

  • Interface scale from 80% to 150%
  • High-contrast palettes and stronger focus indicators
  • Reduced animation and solid/transparency preferences
  • Orca screen-reader integration through AT-SPI

For Orca, open Settings → Accessibility → Screen reader. The page reports whether it is installed and switches the toolkit accessibility bridge and autostart entry. If your screen reader does not announce an app, check the troubleshooting guide and the AT-SPI bus log; do not install packages without understanding the proposed change.

6. Devices, network and printing

Bluetooth

An adapter is required. On VirtualBox, pass through a USB Bluetooth adapter if necessary. Then:

  1. Turn on Bluetooth power.
  2. Put the peripheral into pairing mode.
  3. Select Scan for devices.
  4. Choose Pair, Connect or Remove as appropriate.

Pairing may require a confirmation PIN on both devices. Pairing audio hardware is not guaranteed on a VM without working pass-through support.

Wi-Fi and wired networking

The Network page reads NetworkManager state. Choose a visible network and supply the security key if required. Wired connections normally work automatically in NAT mode.

Printers

The default CUPS packages are included in the image. To add a printer:

  1. Connect the printer or verify that its network address is reachable.
  2. Open Settings → Printers.
  3. Give it a simple name using letters, numbers, ., _ or -, and enter the correct device URI, for example socket://192.168.1.50:9100.
  4. Select Add printer.
  5. Optionally choose Set as default.

CUPS model drivers may still be necessary for specialised features such as duplexing or manufacturer-specific finishing options.

7. Windows and Android applications

These require separate runtimes. They are not native ELF Linux programs.

  • For .exe, .msi and .bat, use Compatibility Wizard → Windows programs.
  • For .apk, use Compatibility Wizard → Android on an installed system, prepare the image and open the nested Android window.

The exact preparation, constraints and error messages are in the Compatibility guide. Read the important notes before installing third-party executables.

8. Power and updates

Power offers lock, sleep, restart and shutdown commands. Restart and shutdown ask for confirmation, but closing applications can still lose unsaved work.

Before updating:

  1. Save documents and close running installers.
  2. Confirm internet access and sufficient disk space.
  3. Check updates from Settings or Store.
  4. Wait for jobs to finish; do not power off during package configuration.

The live guest should never be rebooted by an automated test without your consent.

9. Everyday safety checklist

  • Only run Windows, Android and Linux packages from sources you trust.
  • Do not execute random terminal commands from untrusted websites.
  • Back up files before changing partitions or performing an installation.
  • Keep at least one tested, bootable copy of your working ISO.
  • Install updates deliberately, not in the middle of another installer.
  • Restore demo settings after testing if you share an existing VM.

10. Getting help

Use Troubleshooting for boot, display, API, Store and runtime failures. For VM-first guidance and checksum verification, see Build and deployment.

Compatibility Guide

This guide explains how LuminaOS opens non-native program formats and the practical limits of each runtime.

Important: LuminaOS uses compatibility layers and containers; it does not become Windows, Android or macOS. Per-application testing is essential. Always obtain software from a trusted source.

1. Format dispatch at a glance

File formatRuntime or handlerWhat the UI reports
.exeWineLaunched
.msiWine msiexecInstaller launched; finish it inside Wine
.batWine cmdWindows command process launched
.deblumina-pkg / APTInstallation job
.flatpakref, .flatpakFlatpak / FlathubInstallation job
.AppImageDirect executable / FUSELaunch or installation job, depending on entry point
.rpmAlien, then package managerConversion/install job
.snapSnap daemonInstallation job
.apkWaydroidUser-runtime installation job
.dmg, .pkgCompatibility / archive toolsInspection or native alternatives

Never treat these formats as interchangeable archives. Windows and APK files are deliberately kept out of the privileged Debian package installer.

2. Windows programs through Wine

The image prepares i386 package support and installs Wine32, Wine64 and Winetricks. Compatibility still depends on the Windows program.

First-time setup

  1. Open Compatibility Wizard → Windows.
  2. Review the Wine and Wine-prefix checks.
  3. Choose Set up Wine to initialise the prefix.
  4. If a program needs additional runtimes, use Winetricks selectively.
  5. Open the installer or executable from Files or Store.

Wine's first launch may take time while it creates the Windows environment. Do not repeatedly start installers if the first one is still configuring.

Supported launch paths

  • Portable .exe: starts through Wine. This is a launch, not a system installation.
  • MSI .msi: LuminaOS converts the local filename to a Windows-compatible path and passes it to wine msiexec /i. Complete the vendor installer normally.
  • Batch file .bat: opens with wine cmd /c.
  • Application not yet available: LuminaOS opens the Compatibility Wizard rather than silently doing nothing.

Practical Windows limitations

The following often need application-specific work or cannot be supported by Wine:

  • Kernel drivers, protected storage drivers and low-level antivirus software
  • Applications using unsupported activation, DRM or anti-cheat systems
  • Programs requiring unavailable hardware dongles
  • Some .NET, DirectX, Visual C++ or font dependencies
  • Installers that need OS-specific reboot and service behavior
  • ARM-only Windows executables on an x86-64 VM

Recommended testing order: a portable application first, then a small MSI, then your actual required application. Keep a copy of the original installer and save its exact version.

Safe Winetricks use

Winetricks downloads and installs Windows components into the user's Wine prefix. Review every component; version mismatches can make an otherwise working application fail. Prefer a dedicated prefix for incompatible applications. Do not run unknown DLLs with root privileges.

Bottles and Proton

Bottles and Steam/Proton are optional compatibility managers. They can simplify per-app environments, but they do not make every Windows game or app compatible. Size, GPU performance and anti-cheat restrictions still apply.

3. Android applications through Waydroid

Android requires Waydroid, Weston, binder kernel support and an initialized container. LuminaOS currently uses an X11 desktop, so Android runs inside a nested Weston Wayland window.

Supported target

The automated setup path targets Debian 13 (trixie) and configures:

  • The signed Debian trixie-backports source
  • waydroid and weston
  • The Waydroid container service
  • On first use, a system image selected by the Waydroid initialization command

On unsupported distributions the helper stops with a clear message; it does not execute an unverified third-party installer as root.

Setup and first launch

  1. Use an installed LuminaOS system, not the live session.
  2. Open Compatibility Wizard → Android.
  3. Start Set up Android support and install the offered Waydroid package.
  4. Click Open Android.
  5. Allow the administrator prompts required for container/image setup.
  6. Wait for the first image download and session startup. This can take several minutes and needs reliable internet access.
  7. Install an APK through Files or Store and inspect the running job for its real result.

APK installation behavior

The Store opens lumina-android install /path/to/application.apk as a user-runtime background job. Only an exit status of zero marks the job Installed. First-start, image, session, permission and package errors remain visible in the job log.

Do not judge an install by whether a window merely opened. Check the Android app list after the job succeeds.

Important APK limitations

  • ARM-only APKs are not supported natively by an x86-64 VM. They require a separately validated translation layer. LuminaOS does not silently claim to install such a layer.
  • Android-x86-compatible APKs provide the best starting point.
  • Applications requiring Google certification, SafetyNet/Play Integrity, GPS, telephony, NFC, camera or physical sensors may not work.
  • Google-enabled images require the vendor download and potentially Google account verification/regional terms.
  • Heavy games may be limited by virtual GPU performance and available memory.
  • Waydroid does not make every Play Store application available or compatible.

4. Kali Linux Security Suite

LuminaOS provides a dedicated Kali-themed terminal and a security-tool manager. Most standard tools are installed from Debian; the optional Kali repository is explicitly configured only when requested.

Open the terminal

  • Open Kali Terminal from the application menu, or
  • Run lumina-terminal --kali, or
  • Use Open in Kali Terminal from the Files context menu.

The terminal sources /etc/lumina/kali-profile.sh, with a user-profile fallback. Standard terminal commands still work. Existing x-terminal-emulator alternatives remain attached to a real emulator, not a recursive wrapper.

The kali-tools command

kali-tools list       # report installed security tools
kali-tools top10      # install the standard tool set
kali-tools web        # Burp Suite, SQLMap and Nikto, where available
kali-tools password   # Hashcat, Hydra and Medusa, where available
kali-tools msf        # Metasploit through the validated Lumina helper

Metasploit and the optional Kali repository

  1. Click Configure Kali Repositories in Compatibility Wizard.
  2. Allow the key download and signature-checked source configuration.
  3. Then select Install Metasploit.

Repository setup uses HTTPS, a scoped keyring and a low APT pin-priority. If key or repository signature verification fails, the source is removed and setup fails closed.

Warning: Kali is a rolling distribution. Mixing dependencies with Debian can introduce conflicts even with pinning. APT preview is essential for large Metasploit/security-tool installations. Do not approve an unreviewed full-system upgrade merely to make a package install succeed.

Security tools are dual-use software. Only scan systems and networks you own or have explicit authorization to test.

5. Linux desktop packages

  • Debian .deb: installed through APT so dependencies can be resolved.
  • Flatpak: Flathub and Sandbox configuration may be required.
  • AppImage: launchable directly when the correct FUSE components and execute bit are present; a separate install action can place a trusted image in a system location.
  • RPM: converted through Alien; distribution-specific scripts or dependencies may not translate perfectly.
  • Snap: requires snapd and the system service/socket.

These package managers can modify your system and typically need an administrator prompt. Read the package source, dependencies and planned removals before continuing.

6. macOS files (optional)

DMG and PKG files can be inspected or extracted with the supported tools. Darling provides limited command-line translation where available. Full graphical macOS application compatibility is not provided. For daily work, select a maintained native Linux alternative when available.

7. What to include in a compatibility report

  • File extension, package/application name and exact version
  • Where the file came from and its checksum, if published
  • Installed/runtime versions (Wine, Waydroid, Weston, Flatpak, etc.)
  • Whether it works on the live session or installed system
  • Full job log or error text; never just “it doesn't work”
  • VM resource allocation and kernel/container support for Android

Use tools/validate-guest.py for runtime/file presence checks. That script does not install packages or change settings.

Build and Deployment Guide

This is the release path for producing a LuminaOS image, verifying it and sharing it for VirtualBox evaluation.

1. Release inputs and outputs

Required input: the current LuminaOS source tree and a Linux build environment with administrator access.

Outputs:

LuminaOS-1.1-amd64.iso
LuminaOS-1.1-amd64.iso.sha256
release/build-manifest.json

The checksum establishes file integrity against the published checksum. It is not a replacement for a digital release signature or a successful guest test.

2. Option A — GitHub Actions (recommended on Windows)

The repository includes two workflows:

  • host-tests — source, installer, performance and release checks on relevant pushes.
  • build-iso — manually dispatched Linux build with downloadable ISO artifacts.

Dispatch the ISO build

From the repository root:

gh auth login
# If workflow files have not been pushed yet, request the workflow scope first:
gh auth refresh -h github.com -s workflow

gh workflow run build-iso.yml --ref main
gh run list --workflow build-iso.yml --limit 1

Alternatively, open GitHub → Actions → build-iso → Run workflow.

Monitor progress

Copy the run ID from the output and use:

gh run watch <RUN_ID> --exit-status --interval 60

The workflow has a 120-minute timeout. It installs the Debian build dependencies, validates the source, runs the build, checks the checksum and uploads artifacts. An in-progress run is not evidence of a working ISO.

Download the build

gh run download <RUN_ID> -n LuminaOS-1.1-amd64 -D artifacts

Inspect artifacts/release/build-manifest.json. It records source test outcomes, timestamps, ISO size, hash and guest-validation state.

When a run fails

gh run view <RUN_ID> --log-failed

Do not distribute an ISO from a failed job. Correct the error, rerun the source checks and create a fresh artifact.

3. Option B — local Debian/Ubuntu build

Requirements:

  • x86-64 Debian/Ubuntu Linux or WSL2
  • Administrator access
  • At least 8 GiB free disk; approximately 12 GiB or more is recommended
  • Reliable network access
  • Debian build utilities from tools/build-release.sh

From the LuminaOS-performance directory:

sudo bash tools/build-release.sh

The wrapper installs no guest packages for testing; it constructs a new environment from Debian repositories and the supplied package list. On its first run, the base bootstrap and package download can take considerable time.

The base ISO enables i386 before installing Wine32/Wine64. On Debian 13, Waydroid is not unconditionally included from the main repository; the Android helper configures signed trixie-backports on demand.

WSL2 notes

The workflow under release/wsl2/ provides a source-copy workflow on E:. It may stop WSL after confirmation for consistent export; it does not unregister the original distro. Follow release/wsl2/README.md rather than improvising an import over your working Linux installation.

4. Verify the artifact

On Linux

Run beside the ISO and checksum file:

sha256sum -c LuminaOS-1.1-amd64.iso.sha256

On Windows PowerShell

$expected = (Get-Content .\LuminaOS-1.1-amd64.iso.sha256).Split()[0]
$actual = (Get-FileHash .\LuminaOS-1.1-amd64.iso -Algorithm SHA256).Hash.ToLower()
if ($actual -ne $expected) { throw "ISO checksum mismatch" }
Write-Host "ISO checksum verified: $actual"

A mismatch means the file should not be used. Re-download or rebuild it rather than trying to repair an unknown image.

6. Guest acceptance

Build success is just one stage. Run the read-only guest validator in a booted installed guest:

python3 tools/validate-guest.py

It checks expected API fields, package/runtime presence, Wine, Kali terminal, accessibility and Bluetooth response shapes. It does not install packages or change settings.

For broader non-destructive app checks:

DISPLAY=:0 XAUTHORITY="$HOME/.Xauthority" python3 tools/test-live.py

For an isolated Windows + VirtualBox acceptance run, tools/vm-acceptance.py creates a brand-new VM (and refuses reused names), boots only the live ISO, forwards loopback port 2225 for SSH, uploads just the test scripts to a temporary guest folder, and captures JSON/screenshots locally. Install paramiko in a project-local virtual environment if needed, then run:

python tools/vm-acceptance.py --iso E:\LuminaOS-Artifacts\LuminaOS-1.1-amd64.iso --ram 2048 --basefolder E:\LuminaOS-Acceptance

It never boots/modifies an older VM and never powers the new VM off automatically. Read the reported exit statuses and evidence files; successful boot alone is not a passing release test.

Run that command inside the graphical guest session (or through SSH with the correct display authority). Review its JSON report for failures and warnings. Restore demo settings, close test windows, clear test notifications and do not reset or power off another user's session without permission.

Also complete the relevant rows in:

  • release/QA_MATRIX.md
  • release/RELEASE_CHECKLIST.md
  • release/SIGNOFF_TEMPLATE.md

Required coverage includes live boot, installation, installed boot, settings, apps, network, audio, display and compatibility runtime behavior.

8. Package delivery checklist

Before sending the ISO to someone else:

  • ISO was produced by a successful release workflow or Linux build.
  • SHA256 verification passes on the destination computer.
  • Guest acceptance is documented with any unresolved failures.
  • No secret token, SSH private key, password or personal home-directory content is included.
  • The recipient has the concise SHARE_WITH_FRIEND.md guide.
  • Windows and Android support is described honestly; ARM-only Android apps and app-specific Wine limitations are included.
  • A clear build date and version are visible in the manifest.

9. Rollback and release hygiene

  • Keep the last known working ISO and its checksum.
  • Never overwrite your working VirtualBox VM disk while testing a new ISO; make a separate VM.
  • Do not modify, restart or power off an existing guest merely to test a release.
  • Keep generated ISOs, work/ and environment-specific caches out of source commits.
  • Store release evidence with the source revision that produced it.

Professional release sign-off means repeatable build, verified artifacts and explicit guest evidence, not merely “all apps are implemented.”

Architecture Guide

LuminaOS is a custom desktop built on a Debian 13 base. Its user interface is hosted by GTK/WebKitGTK windows, communicates through a local API, and delegates privileged work to focused package/container helpers.

1. Component map

ComponentRole
src/bin/lumina-sessionStarts and restarts the desktop session; owns session-level startup wiring.
src/bin/lumina-shellHosts desktop, top bar, dock, toast and overlay surfaces on xfwm4
src/bin/lumina-appCreates managed windows for built-in applications; handles window geometry, actions and snapping
src/bin/lumina-terminalSelects a concrete emulator, forwards commands safely and loads Kali profiles when requested
src/lib/lumina/api.pyLoopback HTTP + JSON + Server-Sent Events hub, file/device actions and local job notifications
src/libexec/lumina-pkgDeliberately privileged package, update and optional repository operations
src/libexec/lumina-androidUser-session Waydroid setup, nested Weston startup and APK installation
src/libexec/kali-toolsCLI security-tool reporting and installation routing
src/data/store.jsonStore applications, package ecosystems and categories
system/Live-session, GRUB, Calamares and installed-system configuration overlay
build.shDebian bootstrap, package installation, asset generation and hybrid ISO creation

The UI under src/ui/ contains the shell pages and built-in app surfaces. src/ui/js/lumina.js supplies the shared JavaScript client and actions.

2. Desktop rendering model

lumina-shell hosts separate WebKitGTK windows for desktop components. It uses WNCK and monitoring/layout information to position workspaces, top bar, dock and overlays.

lumina-app hosts higher-level application windows and supports:

  • Per-application default dimensions and single-instance controls
  • Client-side title bars with native window actions
  • Snap layouts, resize areas and transparent rounding/shadows
  • Loading the app's HTML from the local server with serialized launch arguments
  • Message passing between web content and native GTK window management

The shell currently targets X11 with xfwm4 compositing enabled. This is deliberate for VM rendering stability. Android adds a nested Wayland compositor instead of silently replacing the whole desktop session.

3. Local API and event flow

The API listens on 127.0.0.1:7700 by default and does not require exposure to the LAN or internet.

MechanismPurpose
GET routesSystem information, settings, devices, files, Store and readiness checks
POST routesSettings, mutation, jobs and launch/runtime actions
Server-Sent EventsSettings changes, UI commands, app notifications and Store job updates
Shared Lumina clientShared HTTP, application, menu, dialog and settings operations

Mutating routes require X-Lumina-Token, generated per boot and stored at ~/.cache/lumina/api-token with owner-only permissions. Rate limiting and the audit log support basic local-host hardening; the audit log rotates at 1 MiB.

Trust boundary: the loopback API is not intended to be a network service. Do not bind it publicly, proxy it into the internet or publish its token.

4. Application installation and job state

The privileged helper runs through sudo for pre-authorized actions or pkexec for a user-mediated prompt. Package names, printer names and Bluetooth addresses are validated before command execution.

The Store distinguishes these jobs:

  • System packages — privileged APT, Flatpak or file-install actions; progress is streamed through the helper output.
  • Windows launches — direct Wine execution, represented as Launched, not an installed package.
  • APK jobs — asynchronous user-runtime invocations; success is marked only after process exit zero.

Process-spawn failures are captured in the job rather than leaving a stuck “running” job. Empty or unsupported parameters are not silently forwarded to arbitrary commands.

5. Compatibility runtime separation

Wine

open_path() selects specific Windows command forms. MSI and batch filenames are converted using winepath and sent to msiexec and cmd respectively. The file is not reclassified as a Debian package.

Wayland and Android

lumina-android follows a readiness sequence:

  1. Reject the live session and missing runtime tools.
  2. Use an existing Wayland socket when available; otherwise start nested Weston on X11.
  3. Initialize the Android image only if missing, using a privileged prompt.
  4. Start the Waydroid container.
  5. Wait for the Android session before installing an APK or reporting readiness.

This separation means the UI cannot honestly claim that the first button click installed the APK.

Kali

Dedicated terminal launchers use argv arrays for profile paths and concrete emulator choice. They never invoke themselves through the x-terminal-emulator alternative. The package helper validates Kali's archive key, limits its trust to a signed-by keyring and removes the source if verification fails.

6. Settings and user data

Per-user configuration normally lives below:

~/.config/lumina/
~/.cache/lumina/

Defaults cover appearance, performance, accessibility and notifications. Settings updates are applied consistently through the API/client and propagated to interested shell surfaces.

Processes use start_new_session=True for detached application launches, and file-opening helpers use safe path checks rather than shell interpolation. The cwd for terminal actions is validated and falls back to the user's home directory.

7. Performance design

  • Shared CPU-time sampling and cached statistics reduce repeated system reads.
  • Idle work is bounded in desktop, dock, top bar and Task Manager timers.
  • Reduced-motion, transparency, dock magnification and shadow preferences are exposed in Settings.
  • Balanced, custom and powersaver/low-power profiles coordinate the preferences.
  • UI visibility changes and failed pollers release monitoring locks and resume appropriately.

Performance claims require live measurement. Host-source tests do not prove guest boot time, frame rate or memory percentages. Before/after comparisons in a guest should use the benchmark tool and an unchanged workload.

8. Build architecture

The release wrapper tools/build-release.sh checks the Linux host, tool availability and free space, runs source suites, invokes build.sh, and verifies the output SHA256.

The GitHub build-iso workflow runs this process on Ubuntu 24.04 when manually dispatched and uploads:

  • LuminaOS-1.1-amd64.iso
  • LuminaOS-1.1-amd64.iso.sha256
  • release/build-manifest.json

Build output is an artifact for testing/distribution. Successful build plus matching checksum still requires guest boot/installer/installed-boot acceptance before a production sign-off.

Live API suiteNon-destructive desktop and app checks in a booted guest
Guest validatorExpected files, Wine/compatibility endpoints, terminal/Kali support and accessibility state
VirtualBox acceptanceActual live boot, installer, installed boot and user-facing checks

Use tools/test-live.py for broad non-destructive interaction testing and tools/validate-guest.py for read-only built-image validation. Neither replaces a careful manual review of destructive operations such as repartitioning.

10. Extension guidelines

  1. Reuse Lumina client APIs instead of duplicating HTTP and token handling.
  2. Validate all user/package/device identifiers on the server.
  3. Prefer user-session actions; require privilege only when unavoidable.
  4. Never report completion before the actual operation exits successfully.
  5. Keep unrelated user work out of a feature commit.
  6. Add focused regression tests and update release counts/QA documentation together.
